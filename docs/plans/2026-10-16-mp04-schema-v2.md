# MP-04 receipt schema v2

This is the concrete implementation contract for T-116/T-117. It extends the
[financial command contract](2026-10-16-mp04-receipt-contract.md). Migration and receipts are
implemented and independently reviewed; root19 exit0 and the final evidence audit close MP-04.
The independent architecture pass selected
append-only receipt/observation tables; parent review tightened nullable SQL checks below.

## Version and preservation

Freeze `current_v1.sql` and the existing v0-to-v1 migration. Create `current_v2.sql` with exactly
the same domain table/index definitions, replacing only `schema_metadata` with version 2 and
adding the five tables below. Metadata retains the same five columns, but permits only fresh
null provenance or `migrated_from_version = 1` with the actual backup ID/manifest hash. Rebuild
only this metadata table during v1-to-v2 migration. Preserve every other existing table row,
rowid, storage type, ID, event, asset/key reference and `sqlite_sequence` value.

Classification retains exact v0 and v1 recognition and adds exact v2 recognition; only versions
greater than 2 are future. Startup ultimately admits only v2, with explicit `migration_required`
for v0/v1. It never chains upgrades. The existing `migrate` CLI remains the documented explicit
v0-to-v1 command; add an explicit `migrate-v1-to-v2` command rather than infer a target. Keep the
recovery artifact audit v1 frozen. New receipt analysis is a separate audit contract.

## Tables and constraints

All text primary keys explicitly declare `NOT NULL` (SQLite rowid tables otherwise permit a
null text primary key). Monetary/integer checks include `typeof(...) = 'integer'`. Nullable
checks explicitly require non-null values in branches where they are required; SQL CHECK must
not accidentally accept NULL through three-valued logic. All SHA-256 fields require 64 lowercase
hex characters. Operation ID SQL checks match canonical `op-UUID`; application/audit validation
also parses and compares exact canonical UUID spelling.

`bank_operation_receipts` columns:

- `operation_id TEXT PRIMARY KEY NOT NULL`, `receipt_version INTEGER NOT NULL` fixed to 1,
  `operation_kind TEXT NOT NULL` restricted to the five contract kinds.
- `canonical_request_json TEXT NOT NULL`, `request_sha256 TEXT NOT NULL`,
  `source_reference TEXT NOT NULL`, `committed_at TEXT NOT NULL`,
  `event_id INTEGER NOT NULL UNIQUE REFERENCES events(event_id)`,
  `escrow_id TEXT REFERENCES bank_escrow(escrow_id)`, `result_json TEXT NOT NULL`.
- Request/result JSON must be valid objects and exactly match the per-kind contract on audit.
  Source reference and commit time are nonempty. Escrow ID is null for issuance/credit and
  non-null for escrow operations. Partial unique indexes allow one native lock per escrow and
  one native settlement per escrow (release/split share the latter index).

`bank_operation_legs` is WITHOUT ROWID:

- `operation_id TEXT NOT NULL REFERENCES bank_operation_receipts(operation_id)`,
  `leg_index INTEGER NOT NULL` in 0..1, `role TEXT NOT NULL`, `account_id TEXT NOT NULL`,
  `direction TEXT NOT NULL`, `amount INTEGER NOT NULL`, `transaction_id TEXT UNIQUE`,
  `balance_after INTEGER`; primary key `(operation_id, leg_index)`, unique `(operation_id, role)`.
- Roles are account/payer/recipient/worker/poster; directions debit/credit. Positive amounts
  require a non-null transaction FK to `bank_transactions(tx_id)` and integer balance_after
  in 0..SQLite MAX. Zero amounts require null transaction and balance. Account strings are
  nonempty but deliberately have no direct account FK. All FKs use restrictive deletion/update.
- Audit enforces per-kind roles/order/directions/cardinality and that only split legs can be zero.

`bank_legacy_transaction_observations` is WITHOUT ROWID:

- `tx_id TEXT PRIMARY KEY REFERENCES bank_transactions(tx_id)`,
  `cutover_singleton INTEGER NOT NULL` fixed to 1 and referencing the cutover table,
  `observed_kind TEXT NOT NULL`, `observed_fact_sha256 TEXT NOT NULL`.
- Kinds are observed_credit/observed_escrow_lock/observed_escrow_release. Historical credits
  never become reconstructed issuance claims based on a conventional reference or event field.

`bank_legacy_escrow_observations` is WITHOUT ROWID:

- `escrow_id TEXT PRIMARY KEY REFERENCES bank_escrow(escrow_id)`, cutover singleton as above,
  `observed_status TEXT NOT NULL` in locked/released/split,
  `lock_fact_sha256 TEXT NOT NULL`, nullable `resolution_fact_sha256 TEXT`.
- Locked observations require null resolution hash; released/split observations require a
  **non-null** valid hash. A legacy lock may later receive a native settlement without altering
  its lock observation. A historical resolution cannot receive a second settlement owner.

`bank_receipt_cutover` is WITHOUT ROWID with a singleton primary key fixed to 1:

- `attestation_version INTEGER NOT NULL = 1`, `cutover_kind TEXT NOT NULL` fresh_v2/v1_to_v2.
- Nullable `source_schema_version`, `source_migrated_from_version`,
  `source_migration_backup_id`, `source_migration_backup_manifest_sha256` retain the exact old
  v1 metadata provenance (fresh v1 or v0-to-v1). The source version is 1 for migrated cutover.
- Nullable `migration_backup_id`, `migration_backup_manifest_sha256`,
  `migration_plan_sha256`, `source_snapshot_sha256` describe this actual migration.
- Required nonnegative integer `legacy_transaction_count`, `legacy_escrow_count`, and required
  `legacy_transaction_set_sha256`, `legacy_escrow_set_sha256`, `marker_set_sha256`.
- Fresh v2 requires **all** source/migration provenance fields null and both counts zero,
  with the predefined hashes of the empty marker sets. Migrated v2 requires all current
  migration fields and valid exact source provenance. No fake backup or implicit provenance.

Store normalized receipt columns/legs plus canonical request/result JSON; do not duplicate a
serialized full receipt. Reconstruct the immutable public object in fixed leg order.

## Observed facts and audit

All hashes use compact, sorted-key UTF-8 JSON, with exact values and no type coercion:

- Transaction fact: tx_id, account_id, type, amount, balance_after, reference, timestamp, event_id.
- Lock fact: escrow_id, payer_account_id, amount, task_id, created_at, event_id (excludes mutable
  status/resolution fields).
- Resolution fact: escrow_id, observed status, resolved_at, sorted matching escrow_release tx IDs.
- Transaction marker set: array sorted by tx_id of tx_id/observed_kind/observed_fact_sha256.
- Escrow marker set: array sorted by escrow_id of escrow_id/observed_status/lock_fact_sha256/
  resolution_fact_sha256.
- Combined marker hash: object containing attestation_version and the two count/set-hash pairs.

The separate `audit_receipt_ownership()` verifies the existing money audit and total, disjoint
ownership: every transaction has exactly one legacy marker or positive native leg; every escrow
lock has exactly one legacy marker or native lock receipt; every resolved escrow has exactly one
historical resolution or native settlement, and locked escrows have no resolution owner.
It joins positive legs to actual transaction account/amount/balance/event/time/type/reference,
checks request hashes and every per-kind result/leg/effect, and rejects orphan/extra/missing rows.
It recomputes all observed facts and cutover set hashes/counts. Deleting a native receipt creates
an uncovered effect; adding a legacy marker to hide it changes the attestation and fails audit.
Gateway offers no marker/attestation mutation command. Attestation is corruption detection,
not protection against an attacker who can rewrite the entire database and its backups.

## Migration and proof sequence

The separate `migrate_v1_to_v2()` reuses the proven backup-bound source authority and cleanup
discipline: exact v1 verified clone, integrity/FK/money validation, all-domain snapshot, live
BEGIN IMMEDIATE, exact clone/live comparison, sidecar creation and marker publication, metadata
replacement, in-transaction v2/ownership/provenance/preservation checks, one explicit SQL COMMIT,
writer disposal, fresh read-only verification, durable no-clobber evidence. Commit exceptions
remain uncertain; never retry a commit or lose the primary error during cleanup/evidence failure.

Tests precede each slice: malformed IDs and changed commands; legacy cutover and missing-owner
corruption; backup/migration rollback and exact row preservation; native receipt/effect atomicity;
independent-connection opposing settlement races. First add independently testable schema/audit
components, then integrate writer and startup together so startup never admits unowned new money.
Retain all v0-to-v1 proof against its frozen v1 target. Finish with independent review and fresh
isolated root CI before closing either ticket.
