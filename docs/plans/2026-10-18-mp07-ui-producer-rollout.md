# MP-07 UI producer rollout

## Outcome

The local operator UI must act as an explicit MP-07 producer. A poster chooses an
acceptance window when creating a task, and every accept, approve, or dispute
request carries one caller-owned operation ID and the authoritative lifecycle
version read from `board_task_contracts`.

This rollout does not add recoverable task creation (MP-05), submit-bid or
submit-deliverable UI flows, or the complete adapter closure tracked by MP-20.

## Current boundary

- `CreateTaskRequest`, the proxy router, the proxy service, and `task.js` omit
  `acceptance_window_seconds`.
- `get_task_drilldown` reads only `board_tasks`; it does not expose the
  authoritative `board_task_contracts.lifecycle_version`.
- Accept, approve, and dispute proxy routes accept no native operation identity.
- `task.js` treats every resolved proxy fetch as success and immediately refreshes,
  even when the Task Board reports a claimed operation with HTTP 202.
- The shared `TaskBoardMixin` already requires an explicit acceptance window and
  explicit `operation_id` / `expected_lifecycle_version` mutation arguments.

## Contract

### Task creation

The creation form presents `acceptance_window_seconds` as a required positive
integer field. It is a poster decision and is forwarded unchanged through the UI
request model, proxy router, proxy service, and `UserAgent.post_task`. The UI has
no default or inferred value.

Task creation recovery remains outside this rollout. The existing SDK creates the
task ID internally, so retry-safe creation needs the separate MP-05 contract.

### Authoritative lifecycle version

The task drilldown query reads `board_task_contracts.lifecycle_version` in the same
SQLite statement and snapshot as the corresponding `board_tasks` row. The response
exposes that exact integer as `lifecycle_version`; absence of the contract row is
reported as a visible task-contract integrity error. It is not translated to zero
or confused with a missing task/HTTP 404.

### Native mutation requests

The three browser mutation bodies are strict JSON objects:

- accept: `operation_id`, `expected_lifecycle_version`
- approve: `operation_id`, `expected_lifecycle_version`
- dispute: `reason`, `operation_id`, `expected_lifecycle_version`

Missing, extra, malformed, boolean, negative, or non-integer identity fields are
rejected before the `UserAgent` is called. The proxy forwards the exact caller
values to the matching SDK method.

The public response remains the flat Task Board `TaskMutationResponse`: current
task fields at the root plus the immutable `operation` envelope. The UI proxy sets
HTTP 202 when `operation.operation_state == "claimed"` and HTTP 200 when it is
`"completed"`. It does not wrap the task under a second `task` key.

### Browser intent ownership and retry

`task.js` owns at most one frozen mutation intent for a task in browser
`sessionStorage`. The stored intent contains the operation ID, authoritative
expected version, action, action-specific business terms (including bid ID or
dispute reason), the operator agent ID that created it, and no secrets. Operation
IDs are generated by browser code and are not human form fields. Accept, approve,
and dispute each freeze their complete terms before transport.

The first click freezes the intent before transport. Network uncertainty or a
valid HTTP 202 response retains it. A retry, including after a same-tab reload,
reuses the exact path, ID, expected version, and business terms. It must not refresh
the saved intent with a later version or generate a new ID for the same operation.

The saved intent owns an action-independent recovery panel. It remains available
when a lost acknowledgment is followed by a task refresh or reload whose current
view has already reached the command target or a later lifecycle phase, where the
original action button is correctly absent. The panel offers explicit confirmation
retry of the frozen request; it does not auto-retry. A completed replay may contain
the original immutable operation outcome alongside a current task projection that
has advanced beyond that outcome. Matching is against the saved operation, task,
and command rather than requiring the current task view to equal the original
target.

Before signing or replaying, the browser compares the saved `operator_agent_id`
with `/api/proxy/identity`. A changed or unavailable operator leaves the recovery
intent visible and disabled with an identity-mismatch explanation; it never silently
re-signs the saved business intent under a different economic identity.

Pure transitions such as bid acceptance complete atomically and therefore cannot
legitimately return a claimed/pending envelope. HTTP 202 is possible only for
effectful approval or dispute work and is rendered as pending without announcing
approval, payout, or dispute completion.

The browser distinguishes three outcomes for its one task/action intent:

- transport uncertainty retains the frozen intent for exact retry without claiming
  that the server did or did not claim it;
- a valid, matching HTTP 202 acknowledgment records that the server claimed the
  operation and permits exact retry only;
- a typed terminal conflict is displayed as a conflict, not as success or as proof
  that any server-claimed work was cancelled.

Normally, only a structurally valid completed envelope whose task, command, and
canonical operation ID match the frozen request clears the stored intent and
refreshes the task. A foreign operation ID, malformed body, mismatched command/task,
or claimed envelope on HTTP 200 remains visible as an acknowledgment error, retains
the intent, and never announces success.

One narrow rejection path is also terminal: a valid `task_version_conflict` whose
expected version matches the frozen request proves that this operation ID was not
claimed, because native replay lookup precedes version admission. The browser still
retains it without automatic refresh. It may show an operator-bound explicit
"refresh and dismiss rejected operation" control; that control first reads the
authoritative task and clears only when its version/status exactly match the typed
conflict details. The operator may then start a new action with a fresh operation ID
and the newly observed version. Other 409s, transport uncertainty, valid claimed
operations, malformed acknowledgments, and foreign acknowledgments never expose
that dismissal control, so local UI state cannot pretend to cancel server work.

A valid Task Board HTTP 409 error envelope (`error`, `message`, and object
`details`) passes through the UI proxy with its original status and fields. The
browser renders it as a conflict, retains the intent, and does not refresh or
announce success. Malformed/non-object upstream error bodies become a typed UI 502
and receive the same retain/no-success browser treatment.

`sessionStorage` gives same-tab reload continuity without claiming cross-browser or
browser-restart durability. Durable producer recovery beyond that boundary remains
later masterplan work.

## Failing-test-first sequence

1. Add `tests/unit/test_mp07_native_proxy.py` for strict request validation,
   exact SDK forwarding, flat 200/202 responses, and the authoritative drilldown
   version.
2. Add `tests/unit/test_mp07_native_proxy_browser.py` against the shipped
   `task.js`: explicit create-window payload; all three frozen action contracts;
   pending approval; recovery after the task advances and the original action
   disappears; operator-identity binding; typed conflict retention; invalid
   acknowledgment retention; and clearing only after a matching verified
   completion.
3. Run only those files and retain the genuine red output before source edits.
4. Parent review confirms the contract before any UI product changes.
5. Implementation then proceeds through schema, read projection, proxy service,
   proxy router, and browser code, followed by targeted tests, the existing proxy
   and task drilldown suites, browser tests, and UI `just ci-quiet`.

## Open design limits

- The accepted policy gives each poster control of the window; this plan therefore
  specifies no product default, minimum beyond positive integer validation, or
  recommended duration.
- The UI cannot safely offer local abandonment of uncertain or server-claimed work
  until a later recovery contract can establish the authoritative outcome. Exact
  copy and styling belong to implementation review, but silent replacement is
  prohibited.
- Cross-tab coordination is not claimed. If multiple tabs race, the server's native
  version and competing-operation responses remain authoritative.
